# CUGA Migrator

An automated migration toolkit that converts any source agent system into a CUGA SDK implementation. It uses Claude Code agents for all analysis, code generation, testing, and debugging.

## Prerequisites

- Claude Code CLI installed and authenticated (`claude` in PATH)
- API keys / credentials for the source system and the CUGA runtime placed in the env files described below

## Setup before running

**1. Place the source repo**

Copy or clone the source agent system into `migration_from/<source-name>/`.

**(Optional) Auto-generate analyst hints with `source_sync.sh`**

Instead of writing `CLAUDE.md` by hand, run:

```bash
./source_sync.sh <source-name>
```

This scouts the source repo and writes `migration_from/<source-name>/CLAUDE.md` — mapping structure, flagging large files to skip, and listing key entry points. Run it when adding a new source repo or to refresh an existing hint file. If `CLAUDE.md` already exists the agent will update rather than overwrite it.

From inside Claude Code, `/source_sync <source-name>` or plain language (e.g. *"sync source hints for `<source-name>`"*, via `.claude/skills/cuga-source-sync/SKILL.md`) work the same way.

**(Optional) Add a user request to shape the migration**

Create `.cuga-migrator/user_request.md` to give the orchestrator persistent high-level intent. The orchestrator reads this before starting and surfaces it in every sub-agent prompt so it influences architecture choice, naming, and implementation decisions. Useful when you know upfront that you want a specific architecture (e.g. A2A delegation) or have naming conventions to enforce.

Example:
```
# User Request
I want to migrate the cp4i supervisor to a CUGA supervisor, using the A2A approach
to orchestrate the existing cp4i agents as external services.
```

**2. Add ground truth**

Place `.txt` trace files in `migration_to/data/ground_truth/`. Each file must contain a `USER INPUT` section and a `FINAL OUTPUT` section. If you have none yet the pipeline will pause and ask you to provide them before running tests.

**3. Configure credentials**

Three `.env` files are required (all gitignored):

| File | Used by | What to put in it |
|------|---------|-------------------|
| `.env` | migrate.sh, cuga_sync.sh, source_sync.sh | `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_MODEL`, optionally `ANTHROPIC_BASE_URL` |
| `migration_from/.env` | analyst, test_writer | Source system API keys / connection strings |
| `migration_to/.env` | evaluator | CUGA runtime credentials (LLM API keys, MCP server env vars) |

None of these files are generated by the pipeline. Copy `.env.example` to `.env` for the root file and fill in your values. Create the other two manually.

## Keeping templates in sync with the SDK

When you update `migration_to/cuga-agent/` to a new SDK version, run this **before** starting a migration:

```bash
./cuga_sync.sh
```

This reads the updated SDK source, detects drift in the templates, and updates `cuga-templates/` so future `/migrate` runs produce accurate implementations. No arguments needed.

From inside Claude Code, `/cuga_sync` or plain language (e.g. *"sync CUGA templates"*, via `.claude/skills/cuga-template-sync/SKILL.md`) work the same way.

## Running the migration

The preferred way is the shell launcher, which sets credentials, does preflight checks, dispatches a background session, and opens Agent View automatically:

```bash
./migrate.sh <source-name> <target-name> [--stages <stage>[,<stage>...]]
```

**Example:**
```bash
./migrate.sh cp4i-res cp4i-cuga
```

Run without arguments for interactive prompts:

```bash
./migrate.sh
```

Alternatively, if you are already inside Claude Code, run the slash command directly:

```
/migrate <source-name> <target-name> [--stages <stage>[,<stage>...]]
```

Or just ask in plain language, e.g. *"Migrate `<source-name>` to CUGA as `<target-name>`"* — this
goes through `.claude/skills/cuga-migrator/SKILL.md` instead of the slash command, a proper Claude
Code Skill that auto-matches your request against its `description` field (the same mechanism
Bob's `cuga-migrator` skill uses), then parses source/target/stages from your message and follows
the slash command's pipeline logic. Both paths run the identical pipeline.

`--stages` is optional — omit it to run the full pipeline. See "Running specific stages
(`--stages`)" below for what it does and when to use it.

You can watch the analyst, implementer, test_writer, evaluator, and debugger work in the Agent View tree.

### Human review gates

The pipeline pauses **twice** for your review:

1. **After analysis** — the orchestrator summarises `migration_spec.md` and flags any capability gaps. Edit the spec directly if something is wrong, then confirm to continue.
2. **After implementation** — a file list of the generated implementation is shown. Inspect it, then confirm to run tests.

### Eval–debug loop

After your implementation review, the evaluator runs all test cases and scores them. If the overall score is below 0.8 the debugger patches the implementation and the evaluator re-runs — up to 3 cycles. When the loop ends (pass or 3 cycles exhausted) the orchestrator reports the final score and any remaining failures.

### Running specific stages (`--stages`)

To re-run just one stage — or several, in order — instead of the full pipeline, pass
`--stages <stage>` or a comma-separated list:

```bash
./migrate.sh cp4i-res cp4i-cuga --stages analyst
./migrate.sh cp4i-res cp4i-cuga --stages analyst,implementer
```

or, from inside Claude Code: `/migrate cp4i-res cp4i-cuga --stages analyst,implementer`.

Each `<stage>` is one of `analyst`, `implementer`, `test_writer`, `evaluator`, `debugger`. The
orchestrator runs **only** the listed stage(s), in the order given, then stops — no review gates,
no automatic eval-debug looping (`--stages evaluator,debugger` runs each exactly once; it does not
trigger the up-to-3-cycle loop — use the full pipeline for that), and `state.json` is left
untouched. Each stage needs its own prerequisite to already exist on disk — an earlier stage in
the same `--stages` list can satisfy a later one's (e.g. `analyst,implementer` works from scratch,
since analyst produces what implementer needs before implementer's turn). If a prerequisite is
missing you'll get a clear error telling you which stage to run first:

| Stage | Needs on disk first |
|---|---|
| `analyst` | the source repo under `migration_from/<source-name>/` |
| `implementer` | `migration_spec.md` (run `--stages analyst` first) |
| `test_writer` | ground truth `.txt` files under `migration_to/data/ground_truth/` |
| `evaluator` | `test_cases.json` and `migration_spec.md` (run `--stages implementer`/`--stages test_writer` first) |
| `debugger` | `eval_report.json` (run `--stages evaluator` first) |

## Directory layout

```
migration_from/          # put source repos here (one subfolder per project)
  <source-name>/         # source agent repo — add a CLAUDE.md here for migration hints
  .env                   # source system credentials (used by analyst/test_writer)
migration_to/            # generated CUGA implementations land here
  cuga-agent/            # CUGA SDK (reference for implementer + runtime for evaluator)
  <target-name>/         # generated implementation
  data/
    ground_truth/        # ground truth .txt files (input + expected output)
    prediction/          # eval outputs (one entry per test case, run in parallel)
      actual_outputs/    # <test_id>.json per test case
      traj/              # <test_id>/ activity logs per test case
      eval_report.json   # overall scores and failure analysis
    debug_log/           # debug_<iteration>.md per debug cycle
  .env                   # CUGA runtime credentials (used by evaluator)
cuga-templates/               # CUGA scaffolds — define the exact structure of a CUGA application
  supervisor/            # supervisor architecture (CugaSupervisor + internal CugaAgents via MCP)
  a2a_supervisor_external/ # supervisor architecture (CugaSupervisor + external agents via A2A)
  one_agent/             # one_agent architecture (single CugaAgent + skills)
  tests/                 # test runner template
.cuga-migrator/    # pipeline state, spec, eval reports (auto-generated)
  migration_spec.md             # analyst output: architecture design document
  source_summary.md             # analyst intermediate notes on the source repo
  state.json                    # pipeline progress tracker
```

## Pipeline stages

| Stage | Agent | What it does |
|-------|-------|-------------|
| 1 | `analyst` | Reads source repo + CUGA SDK + templates → writes `migration_spec.md` |
| 2 | `implementer` | Reads `migration_spec.md` + templates → writes complete CUGA implementation |
| 3 | `test_writer` | Reads ground truth → writes `test_cases.json` |
| 4 | `evaluator` | Runs agent for each test case, LLM-judges outputs → writes `eval_report.json` |
| 5 | `debugger` | Reads failures → patches implementation |

Stages 4–5 loop up to 3 times. Human review gates occur after stage 1 and after stage 2.

## Providing hints to the migration

### User request (`.cuga-migrator/user_request.md`)

Create this file to express high-level intent for the migration. The orchestrator reads it before starting and passes it to every sub-agent so it shapes their decisions throughout the pipeline. Useful for:
- Specifying the target architecture (`supervisor`, `a2a_supervisor_external`, `one_agent`)
- Expressing preferences about how existing agents should be wrapped or reused (e.g. "orchestrate existing agents via A2A rather than rewriting them")
- Setting naming conventions or output format expectations

### Analyst hints (`migration_from/<source-name>/CLAUDE.md`)

Create a `CLAUDE.md` at the root of your source repo. The analyst reads it first before exploring the source. Useful things to include:

- Entry point file(s)
- Folders to ignore (legacy code, build artifacts)
- Platform-native features with no source code (capability gaps)
- Expected output format or schema

## Ground truth

Place `.txt` trace flow files in `migration_to/data/ground_truth/`. Each file must have a `USER INPUT` section and a `FINAL OUTPUT` section. If no ground truth exists, the pipeline will ask you to provide it before running tests.

## Resuming

If a migration was interrupted, run `./migrate.sh <source-name> <target-name>` again. The orchestrator reads `.cuga-migrator/state.json` and skips completed stages.

## Read-only directories

These must never be modified during a migration:

| Directory | Reason |
|-----------|--------|
| `migration_to/cuga-agent/` | CUGA SDK runtime — shared dependency |
| `migration_from/` | Source repo — read-only reference |
| `migration_to/data/ground_truth/` | Evaluation source of truth |
