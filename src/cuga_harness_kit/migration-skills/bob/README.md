# CUGA Migrator (Bob)

The Bob port of [`cuga-migrator-claude`](../cuga-migrator-claude/) — an automated migration toolkit that
converts a source agent system into a CUGA SDK implementation. Where the original uses Claude
Code sub-agents, slash commands, and a hook, this version runs the same pipeline as three
[Bob skills](https://bob.ibm.com/docs/ide/features/skills), since Bob has no equivalent to named
sub-agent files, explicit `/commands`, or hooks. See
[`../../BOB_CONVERSION_PLAN.md`](../../BOB_CONVERSION_PLAN.md) for the full gap analysis and
rationale.

**Confirmed via [`../../bob-agent-test/`](../../bob-agent-test/):** Bob subagents in this environment
run strictly sequentially with real per-spawn overhead — not concurrently. The pipeline below is
built entirely around one-subagent-at-a-time execution; there is no fan-out.

## Prerequisites

- Bob IDE, with this folder open as the active project (so `.bob/skills/` and `.bob/mcp.json`
  are discovered)
- API keys / credentials for the source system and the CUGA runtime, placed in the env files
  described below
- **This folder trusted by Bob.** Run `bob` here interactively once and choose "Trust folder"
  before ever using `--yolo`/the launch scripts below. In non-interactive mode Bob silently
  overrides `--yolo` for untrusted folders and falls back to a read-only safe mode — no files get
  written and no skill activates, with no error printed. See
  [Trusted folders](https://bob.ibm.com/docs/shell/security/trusted-folders). Also check Bob
  Settings → Auto-Approve → **Skills** is enabled, since skill activation itself is a separate
  approval gate from file-write approval.

## Setup before running

**1. Place the source repo**

Copy or clone the source agent system into `migration_from/<source-name>/`.

**(Optional) Auto-generate analyst hints**

Instead of writing `CLAUDE.md` by hand, ask Bob to run source sync, e.g.:

> "Sync source hints for `<source-name>`"

This should activate the `cuga-source-sync` skill, which scouts the source repo and writes
`migration_from/<source-name>/CLAUDE.md` — mapping structure, flagging large files to skip, and
listing key entry points. Run it when adding a new source repo, or to refresh an existing hint
file (it updates rather than overwrites an existing one).

Or run `./source_sync.sh <source-name>` — see "Launch scripts" below.

**(Optional) Add a user request to shape the migration**

Create `migration_to/.cuga-migrator/user_request.md` to give the orchestrator persistent
high-level intent. It's read before the pipeline starts and surfaced in every stage's subagent
prompt, so it influences architecture choice, naming, and implementation decisions. Example:

```
# User Request
I want to migrate the cp4i supervisor to a CUGA supervisor, using the A2A approach
to orchestrate the existing cp4i agents as external services.
```

**2. Add ground truth**

Place `.txt` trace files in `migration_to/data/ground_truth/`. Each file must contain a
`USER INPUT` section and a `FINAL OUTPUT` section. If none exist, the pipeline pauses and asks
you to provide them before running tests.

**3. Configure credentials**

Three `.env` files are required (all gitignored):

| File | Used by | What to put in it |
|------|---------|-------------------|
| `.env` | (optional) Langfuse tracing for the generated implementation | see `.env.example` |
| `migration_from/.env` | source_sync stage, test_writer stage | Source system API keys / connection strings |
| `migration_to/.env` | evaluator stage | CUGA runtime credentials (LLM API keys, MCP server env vars) |

Unlike the Claude Code version, there's no root-level `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_MODEL`
— Bob manages its own model credentials at the IDE/tool level, not per-project.

None of these files are generated by the pipeline. Copy `.env.example` to `.env` for the root
file and fill in your values. Create the other two manually.

## Keeping templates in sync with the SDK

When you update `migration_to/cuga-agent/` to a new SDK version, run this before starting a
migration:

> "Sync CUGA templates against the SDK"

This should activate the `cuga-template-sync` skill — it reads the updated SDK source, detects
drift in the templates, and updates `cuga-templates/` so future migrations produce accurate
implementations.

Or run `./cuga_sync.sh` — see "Launch scripts" below.

## Running the migration

Ask Bob something close to the `cuga-migrator` skill's trigger phrasing, e.g.:

> "Migrate `<source-name>` to CUGA as `<target-name>`"

Bob will prompt for approval before activating the skill (unless skill auto-approve is enabled in
settings). There's no explicit `/migrate <args>` invocation the way Claude Code has a slash
command — phrase the request naturally and let Bob's description-matching pick up the skill.

Or run `./migrate.sh <source-name> <target-name> [--stages <stage>[,<stage>...]]` — see "Launch
scripts" below. `--stages` is optional — omit it to run the full pipeline. See "Running specific
stages (`--stages`)" further down for what it does and when to use it.

## Launch scripts

`migrate.sh`, `source_sync.sh`, and `cuga_sync.sh` port the original Claude Code launchers
(`migrate.sh`, `source_sync.sh`, `cuga_sync.sh` in `../cuga-migrator-claude/`) to Bob Shell.

**`migrate.sh` is always interactive**, full pipeline or `--stages` alike. `bob -p` (Bob Shell's
non-interactive CLI mode) is documented as single-shot and non-resumable — it can't pause mid-run
and wait for a reply, so it can't reliably handle the trust-folder prompt, the skill-activation
prompt, or (full pipeline) the two human review gates. `--stages` only changes what the supervisor
is told to do (run just these stage(s), in this order, instead of the full pipeline) — not how the
session is dispatched. So `migrate.sh` always does the usual prep (credentials, preflight checks,
plan summary), prints the constructed request, then opens a plain interactive `bob` session:

```bash
bob --auth-method api-key
```

...and asks you to paste that request as your first message. From there Bob's normal prompts —
trust folder (if not already trusted), activate the `cuga-migrator` skill, each file write, each
review gate if any — all work exactly as they would if you'd typed the request yourself. There's
no way to auto-send that first message (no documented flag to seed an interactive session), so the
one-time copy/paste is unavoidable.

**Before it opens bob, the script copies that request to your clipboard** (`pbcopy` /
`xclip` / `xsel`, whichever is available) and saves it to
`migration_to/.cuga-migrator/last_prompt.txt` — because bob's interactive TUI typically clears the
terminal on launch, wiping out the printed text before you'd get a chance to read it back. **If bob
opens and appears to just sit there doing nothing**, that's not a hang — it's idle, waiting for
your first message. Paste (the request is already in your clipboard) and press Enter.

**`source_sync.sh` and `cuga_sync.sh` stay non-interactive** — neither has anything resembling a
review gate, so they run straight through via Bob Shell's non-interactive CLI mode (confirmed at
`docs/shell/getting-started/start-bobshell-non-interactive`):

```bash
bob --auth-method api-key --yolo -p "<prompt phrased to match the target skill's description>"
```

**Two things these scripts do NOT replicate, because Bob doesn't document an equivalent:**

- **Background dispatch + Agent View.** The original used `claude --bg "..." --name "..."` then
  `claude agents` to open a live session tree you could peek at or attach to. Nothing like that is
  documented for Bob Shell — `migrate.sh` just runs `bob` in the foreground, so you're present for
  the whole run rather than able to detach and reattach later.
- **An explicit "run skill X" flag.** There's no `bob --skill cuga-migrator` equivalent. Prompts
  are phrased to closely match the target skill's `description` field instead, the same way you'd
  phrase it interactively — Bob's own description-matching decides whether to activate it. If it
  doesn't activate, that's a prompt-wording problem to iterate on, not something the script can
  force.

**For the non-interactive scripts specifically** (`source_sync.sh`, `cuga_sync.sh`): if a run
finishes instantly with no files written and no skill activated, the folder almost certainly isn't
trusted yet — `--yolo` is silently overridden in non-interactive mode for untrusted folders, per
[Trusted folders](https://bob.ibm.com/docs/shell/security/trusted-folders). Both scripts print a
warning before running if `~/.bob/trustedFolders.json` doesn't appear to list this directory — but
the check is a heuristic (path substring match) and can't detect "trust parent folder," so treat a
missing warning as reassuring but not definitive. Fix: run `bob` here interactively once and choose
"Trust folder," and confirm Bob Settings → Auto-Approve → **Skills** is on. (`migrate.sh` prints
the same heads-up, but since it's interactive an untrusted folder just shows you the normal trust
prompt instead of silently degrading.)

Credentials: set `BOBSHELL_API_KEY` in `.env` (see `.env.example`) before running any of these.

### Human review gates

The pipeline pauses twice for your review, same as the original:

1. **After analysis** — the orchestrator summarizes `migration_spec.md` and flags any capability
   gaps. Edit the spec directly if something is wrong, then confirm to continue.
2. **After implementation** — a file list of the generated implementation is shown. Inspect it,
   then confirm to run tests.

### Eval-debug loop

After your implementation review, the evaluator stage runs all test cases and scores them. If the
overall score is below 0.8, the debugger stage patches the implementation and the evaluator
re-runs — up to 3 cycles, run strictly one subagent at a time. When the loop ends (pass or 3
cycles exhausted), the orchestrator reports the final score and any remaining failures.

### Running specific stages (`--stages`)

To re-run just one stage — or several, in order — instead of the full pipeline:

```bash
./migrate.sh cp4i-res cp4i-cuga --stages analyst
./migrate.sh cp4i-res cp4i-cuga --stages analyst,implementer
```

or phrase it naturally and let Bob's description-matching pick it up, e.g. "just re-run the
analyst then implementer stages for cp4i-cuga". Each `<stage>` is one of `analyst`, `implementer`,
`test_writer`, `evaluator`, `debugger`. The orchestrator runs **only** the listed stage(s), in the
order given, then stops — no review gates, no automatic eval-debug looping (`--stages
evaluator,debugger` runs each exactly once; it does not trigger the up-to-3-cycle loop — use the
full pipeline for that), and `state.json` is left untouched. Each stage needs its own prerequisite
to already exist on disk — an earlier stage in the same request can satisfy a later one's (e.g.
"run analyst then implementer" works from scratch, since analyst produces what implementer needs
before implementer's turn). If a prerequisite is missing you'll get a clear error telling you
which stage to run first:

| Stage | Needs on disk first |
|---|---|
| `analyst` | the source repo under `migration_from/<source-name>/` |
| `implementer` | `migration_spec.md` (run the analyst stage first) |
| `test_writer` | ground truth `.txt` files under `migration_to/data/ground_truth/` |
| `evaluator` | `test_cases.json` and `migration_spec.md` (run implementer/test_writer first) |
| `debugger` | `eval_report.json` (run the evaluator stage first) |

## Directory layout

```
migration_from/          # put source repos here (one subfolder per project)
  <source-name>/         # source agent repo — add a CLAUDE.md here for migration hints
  .env                   # source system credentials
migration_to/            # generated CUGA implementations land here
  cuga-agent/             # CUGA SDK (reference for the implementer stage + runtime for the evaluator stage) — not shipped, clone it here yourself
  configurations/         # CUGA runtime settings (modes/, models/) — ported unchanged from cuga-migrator
  <target-name>/          # generated implementation
  data/
    ground_truth/         # ground truth .txt files (input + expected output)
    prediction/           # eval outputs (actual_outputs/, logs/, eval_report.json)
    debug_log/             # debug_<iteration>.md per debug cycle
  .env                    # CUGA runtime credentials
  .cuga-migrator/          # pipeline state, spec, eval reports (auto-generated)
    migration_spec.md       # analyst stage output
    source_summary.md       # analyst stage intermediate notes
    state.json               # pipeline progress tracker
    user_request.md          # (optional) your high-level migration intent
    sync_report.md            # cuga-template-sync output
cuga-templates/               # CUGA scaffolds — define the exact structure of a CUGA application
  supervisor/             # supervisor architecture (CugaSupervisor + internal CugaAgents via MCP)
  a2a_supervisor_external/ # supervisor architecture (CugaSupervisor + external agents via A2A)
  one_agent/               # one_agent architecture (single CugaAgent + skills)
  tests/                   # test runner template
.bob/
  skills/
    cuga-migrator/
      SKILL.md               # 5-stage pipeline orchestrator (full + --stages mode)
      agents/                # one file per stage agent, read by the orchestrator at spawn time
        analyst.md               # mirrors cuga-migrator/.claude/agents/analyst.md
        implementer.md
        test_writer.md
        evaluator.md
        debugger.md
    cuga-source-sync/       # standalone: scout a new source repo
    cuga-template-sync/     # standalone: sync templates with the current SDK
  mcp.json                  # MCP server registrations (none by default)
migrate.sh                  # launch script -> cuga-migrator skill (see "Launch scripts")
source_sync.sh              # launch script -> cuga-source-sync skill
cuga_sync.sh                 # launch script -> cuga-template-sync skill
```

Each `SKILL.md` follows [Bob's skill format](https://bob.ibm.com/docs/ide/features/skills): a
`name`/`description` frontmatter pair Bob matches your request against to decide whether to
activate it, plus the instructions themselves. `cuga-migrator/agents/*.md` are supporting files
alongside `SKILL.md`, read by the orchestrator at each stage's spawn time rather than held in
context all at once — mirroring the original Claude Code project's one-file-per-agent layout
(`cuga-migrator/.claude/agents/<name>.md`), just accessed via `Read` instead of a named
`agent_name=` parameter, since Bob has no built-in custom sub-agent definitions.

## Pipeline stages

| Stage | What it does |
|-------|-------------|
| 1. analyst | Reads source repo + CUGA SDK + templates -> writes `migration_spec.md` |
| 2. implementer | Reads `migration_spec.md` + templates -> writes complete CUGA implementation |
| 3. test_writer | Reads ground truth -> writes `test_cases.json` |
| 4. evaluator | Runs the generated agent for each test case, LLM-judges outputs -> writes `eval_report.json` |
| 5. debugger | Reads failures -> patches implementation |

All 5 stages run inside the single `cuga-migrator` skill, each spawning one subagent in
turn — never concurrently. Stages 4-5 loop up to 3 times. Human review gates occur after stage 1
and after stage 2.

## Resuming

If a migration was interrupted, just ask again — the orchestrator reads
`migration_to/.cuga-migrator/state.json` and skips completed stages.

## Read-only directories

These must never be modified during a migration:

| Directory | Reason |
|-----------|--------|
| `migration_to/cuga-agent/` | CUGA SDK runtime — shared dependency |
| `migration_from/` | Source repo — read-only reference |
| `migration_to/data/ground_truth/` | Evaluation source of truth |

## What's different from the Claude Code version

See [`../../BOB_CONVERSION_PLAN.md`](../../BOB_CONVERSION_PLAN.md) for the full analysis. In short:

- **5 named sub-agent files → a `agents/` subfolder inside the skill.** Bob has no equivalent
  to `.claude/agents/<name>.md` (no custom sub-agent definitions — only generic subagent types),
  so each stage's agent definition lives in its own file under
  `.bob/skills/cuga-migrator/agents/`. The orchestrator's `SKILL.md` reads the relevant file in
  full immediately before spawning that stage's subagent, keeping `SKILL.md` itself down
  to pipeline logic instead of one 450+ line file with all five agent definitions inlined.
- **3 slash commands → 3 skills.** `/migrate`, `/source_sync`, `/cuga_sync` are now
  `cuga-migrator`, `cuga-source-sync`, `cuga-template-sync`, activated by Bob matching your
  request against each skill's description rather than an explicit `/name` invocation.
- **The `PreToolUse` logging hook is dropped.** It was diagnostic only — the pipeline never read
  it back — and Bob has no documented hook mechanism to replicate it with.
- **No concurrent fan-out.** An earlier revision of the conversion plan explored spawning
  multiple subagents at once (parallel analyst exploration, parallel debugger patches per failure
  category). Empirical testing in `../../bob-agent-test/` showed Bob subagents run strictly
  sequentially here, so that design was dropped — every stage below spawns one subagent at a
  time.
